# Choose an approach

**Inputs:** authorized unit/revision (or root framing draft), decision drivers, applicable decisions, investigation reports, owned report/decision paths.

**Procedure:**
1. Define the immediate question at the unit's decision horizon. Identify plausible alternatives, including a smaller or reversible one, and assess evidence and uncertainty against the drivers.
2. Distinguish a routine local choice (document in the attempt) from a consequential one (draft from `.agents/workflow/decision.md` with explicit applicability and status `proposed`, only when assigned sole record writer). For meaningful choices, report question/settled position or proposal, category/status, scope, alternatives including rejected options, concise rationale and source/evidence/actual authority for the assigned brief writer's `Decision log`. Missing historical alternatives/rationale are `unknown/not recorded`; label new comparisons and present worker inference, not invented user deliberation. Update the log only when expressly assigned sole brief writer; otherwise hand off the report for incorporation before the writer claims current completeness. Avoid wholesale re-planning, microaction logs and routine-choice microapprovals.
3. Check for conflicts with inherited decisions. To change one, stop affected work and propose an explicit scoped exception or supersession linked to the previous decision and identify affected units, retaining original rationale. Do not mark it approved until the user explicitly accepts its scope. D/checkpoints remain authoritative; newer/local summaries have no precedence, proposed relationships have no effect, and approved exceptions leave the general choice effective elsewhere. Follow protocol approval and bidirectional-link rules with assigned writers.
4. State consequences, observable review signals, and the next bounded action.

## Conditional method: material testing strategy

Use this method before affected substantial software delivery when testing commitments materially affect behavior, quality, risk or effort, including existing-code changes without architecture redesign. When architecture is relevant, coordinate with `code-architecture`; no mandatory PRD/platform stage or separate strategy unit follows. Validate/reuse adequate specifically reviewed current strategy first. A tiny exact existing issue may instead record approved acceptance, a meaningful failure-detecting focused regression and honest limits in a concise sourced brief/report; do not manufacture two runner choices or a review ceremony.

1. Ground drivers in current scenarios and acceptance: concrete starting state → normal/error/recovery action → observable outcome, quality expectations, actual sources/status/current review and applicable brief/D authority. For existing code, read actual executable and test paths and changed risks. Trace accessibility/device, security/privacy/identity, durability/recovery/retention, operations/effort/cost and performance risks **when relevant**. Requirements define expected behavior; testing selects evidence. Missing expectations stay open/conditional with owner/action, not invented features, numerical targets or exclusions. Product latency and test-feedback latency are different.
2. Compare **at least two plausible implementable material strategies for those same cases**, fairly describing each best case, confidence gained, failure surfaces exposed/missed, setup and maintenance, repeated human and operating costs, feedback latency, determinism/flakiness and runtime/tool/service/device feasibility. For example, risk-weighted domain + real-boundary automation + targeted served-browser regressions versus domain + real-boundary automation + recorded manual real-browser release flows can differ materially in repeatability, UI blind spots, infrastructure and human effort. Neither is a default; recommend conditionally from sourced drivers. A runner/library list or an evidence ladder alone is not a strategy comparison. Label qualitative estimates; invent no benchmarks.
3. Make a critical coverage-to-evidence map (table or equally concrete prose):

   `scenario/acceptance/quality → actual source/status/current review applicability → normal/error/recovery risk → concrete input/state + method/check level + expected observable → expected evidence/limits → version-scoped primary source + runtime/service/device prerequisites and separately observed local capability → planned-unrun / blocked-prerequisite / link to separate exact executed target, environment, method and result → affected dependency, open owner/action, deferral or authorized exclusion basis`.

   Cross-cutting risks may need several checks. Unavailable difficult checks remain visible, not silently excluded. Preserve distinctions: domain fixtures exercise rules; mocks isolate handling; real integration exercises the named boundary; served real-browser flows exercise named engines/viewports/states; manual/assistive checks establish only observed outcomes. Build/typecheck/HTTP 200/DOM simulation/mocks prove no actual browser/storage/recovery/learning behavior. Approval proves no execution; independent verification may add necessary checks beyond a weak plan. The [pre-code reference's four-level matrix](../code-architecture/references/greenfield-product.md#3-compare-feasible-verification-not-just-libraries) supplies detailed evidence limits, not a mandatory greenfield route.
4. Support tool/platform recommendations with primary documentation matched to the actual release/version, or dated online docs with version uncertainty/compatibility limits. Separately record local versions and **how** compatibility/launch/service/device capability was observed; docs or binary presence are not a successful launch/test. Missing/incompatible runner, browser binaries/OS dependencies, service or assistive/device setup retains owner/next check and affected claim. Do not automatically install/provision, adopt recurring cost or shrink support. Adequately settled feasible future tests may remain planned-unrun before app code; that alone does not block implementation authority.
5. Produce an assigned, separately owned **concise user-facing strategy artifact**, distinct from detailed report/compact receipt: sourced drivers, meaningful alternatives/recommendation/conditions, critical coverage and evidence limits, prerequisites, prioritized questions and affected readiness. Hand it through the orchestrator's full discussion/answer-artifact route for actual read/relay. Retain stable version/content or individually identified exact statements, path/version and hash or retained copy where useful, actual presentation reference and scope, actual response/quote/reference and statement-specific applicability through owned artifacts/assigned writer. A complete stored unseen strategy or generic architecture/stack/storage approval remains unreviewed. Partial/pending/declined/conflicting reply cannot agree the remainder, v2 or unstated future defaults. An authorized draft/open handoff can finish without claiming dependent build ready.
6. Before affected material commitments, consume sufficient actual scoped review/coverage/feasibility. Reuse unchanged adequate specifically reviewed strategy with exact prior version/statements/presentation/response; add only gaps, no repeat ceremony. Routine runner/fixture/test-case/naming/sequence choices within reviewed authority remain delegated. Material outcome/acceptance/quality/platform/support/effort/cost or inherited changes use applicable D/material revision/checkpoint gates, pausing only affected dependencies while unrelated authorized work continues. Artifacts/review are evidence, not authority stores or unnamed-child authorization; preserve distinct own-unit investigation and sole-writer log handoff.

Executable teaching examples/solutions needing runtime confidence use proportionate alternatives/coverage, reconstruction/dependency prerequisites, expected outputs and checks of normal/error behavior and correctness **for the right reason**, with framework/browser/learning flows where relevant. Distinguish illustrative/mocked from actually executed published code and correctness from learner effectiveness. Pure prose/travel uses fitting domain-primary-source/scenario/usefulness review, not software tests or architecture.

**Output:** comparison in the attempt report; if consequential, proposed decision record and request for checkpoint; compact receipt per `.agents/workflow/protocol.md`.

For material testing choices, also hand off the separately owned concise strategy artifact and exact presentation/review/coverage/prerequisite basis (or honest pending handoff) for affected dependency consumption. The report retains detailed comparison, meaningful choice handoff and evidence; the compact receipt does not become the user discussion.

**Stop/escalate:** drivers or evidence too weak for a consequential choice, or a proposal would exceed approved boundaries. Do not proceed as though a proposed record were effective.
