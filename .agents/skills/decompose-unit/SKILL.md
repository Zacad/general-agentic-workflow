# Decompose a unit

**Inputs:** authorized parent/revision, acceptance criteria, constraints, dependencies, linked accessible own-parent investigator report, available evidence, assigned child-brief paths.

**Procedure:**
1. Read/check the parent's distinct investigator report for current applicability per protocol before substantive preparation; stop evidence gaps for renewed parent investigation. Compare plausible semantic split vectors including no-split per protocol Work split, favoring independently useful completion/review/check/retry boundaries despite shared sources/runtime. Explain the selected current horizon from actual evidence; isolated file/layer/phase fragments are not outcomes. If no children fit, justify the single-horizon leaf; unresolved sizing stays provisional with question/evidence/owner/action. Prepare only the next useful set, not a complete speculative hierarchy.
   For a substantial greenfield multi-feature product, an approved root may first prepare a requirements child with an owned, user-reviewable PRD/equivalent outcome and open-question handoff (`product-requirements` once that child is separately checkpointed). After actual review, prepare an architecture/test-strategy child if product-level alternatives need their own checkable outcome (`code-architecture` greenfield branch), or use `choose-approach` and a scoped consequential decision review when no child is needed. Proposed PRD or architecture content does not settle choices; ask the user to prioritize agreed versus open scope and resolve material commitments before dependent build. Do not confuse a local development/static server or replaceable runner with a deployed backend.
   For substantial unresolved nonsoftware scope, normally prepare a separately reviewable specification/coverage outcome before dependent delivery, using `endeavor-requirements` for authorized discovery or adequate specifically reviewed current-input reuse. Select a requirements child only if independent acceptance/dependency warrants it; neither every tiny leaf nor every domain needs that stage. Do not import software architecture into course/trip work. Before preparing dependent delivery, consume the protocol's coverage trace for **every requested material dimension**: actual source/status/current review → expected content/outcome/depth → current outcome or descriptive provisional horizon → failure-detecting check → dependency/readiness, gap owner/action, deferral or explicit authorized exclusion basis. Missing dimensions are gaps; generic labels/checks or omitted-as-excluded fail. Each material acceptance item needs sufficient actual scoped agreement or applicable approved brief/D authority before dependent readiness/checkpoint; retain pending/partial/declined choices and pause only affected commitments. An authorized discovery child may deliver a draft/open review handoff without claiming dependent readiness.
2. Draft named child briefs using `.agents/workflow/unit.md` with independently checkable outcomes, boundaries, inputs, inherited decisions, dependencies and next action. Cite parent research as input, mark own-child investigation not yet invoked, and schedule the child's distinct investigator first after its named checkpoint to validate/reuse that evidence. Do not run child investigations to complete parent preparation. Mark a child `ready`, revision 1, with no authorization yet **only when its material scope is settled enough for that outcome**; otherwise keep it provisional/blocked pending the named question.
   Record each current proposed child's bounded outcome, dependencies, readiness questions/owner/action, contribution to parent criteria and completion/review/check horizon in the parent's Work split. Give every child brief its own reasoned Work split from parent preparation evidence, including specific leaf rationale or proposed finer boundaries; its own investigator reassesses those boundaries at actual authorized entry. Preparation does not authorize grandchildren. Retain later branches as provisional rather than drafting them all.
   As each child's assigned sole writer, populate its mandatory `Decision log` per protocol: all meaningful established user/reviewed requirements, applicable inherited parent/protocol/D positions and settled local preparation/approach/check/split/dependency choices, with question/position, category/status, scope, alternatives, concise rationale and source/actual authority. Cite specific applicable positions, not a generic ancestor link; D summaries link scoped approval and explicit approved exception/supersession with original rationale and impacted units. Separate proposals/open alternatives, label new comparisons/inferences, and use `unknown/not recorded` for absent historical options/rationale. Check coverage before calling the brief complete; a log neither settles open product choices nor grants child entry.
   Once product inputs and consequential architecture choices are settled enough, prepare only one or a small current group of **vertical feature slices**, each delivering a user-visible flow across relevant UI, rules/state, storage/API and tests rather than separating work by technical layer. Give each concrete starting state → action/exception → observable result acceptance examples, check method, precisely owned output paths and dependencies on reviewed requirements/decisions and other slices. **Before calling a slice ready or checkpointable**, map *each* material acceptance item and implied data/state transition to its specific reviewed PRD statement or actually applicable approved decision/brief clause with source, status and scope. Trace terminal outcomes through save retention/retirement, resumability, history and scoring where relevant: agreement on a no-move loss or on save timing does not settle how an unfinished save is treated after completion. Do not promote a worker proposal, narrative assumption, fictional fixture or broad root approval into agreement. If a needed choice is open, proposed or declined, record the question, decision owner and affected acceptance/dependency, and keep that slice provisional/blocked; unaffected authorized analysis or slices may proceed. Routine choices already covered by approved scope need no new approval.
   Before affected substantial software slice readiness/checkpoint, also consume the exact applicable sufficiently reviewed testing strategy, critical scenario/quality coverage and feasible prerequisites per protocol and `choose-approach`/`code-architecture`. Trace each affected acceptance/state risk to concrete input/state, method/check level, expected observable, evidence/limits and version/prerequisite status; link exact presented statements/version and actual scoped response, not a stored unseen plan or generic architecture approval. Retain pending/partial/declined review and gap owner/action, keeping only affected commitments provisional. Feasible agreed pre-code checks may remain planned-unrun; approval/build/HTTP/mocks are not executed browser/storage/recovery evidence. Reuse adequate specifically reviewed unchanged strategy; tiny exact issues may use concise approved acceptance/meaningful regression/honest limits. Prepare a separate strategy outcome only when independent acceptance/dependency warrants it, checkpoint before own investigator; no routine runner microapproval. Material scope/support/platform/effort/cost/quality changes follow D/revision gates, while unrelated authorized work continues.
   Before affected material UI slice readiness/checkpoint, consume the protocol's visual-review basis: sufficient actually reviewed direction/assets/constraints/response or validated adequate reviewed reuse/tiny basis for the current audience/tasks/platform/states. Trace each affected acceptance item to exact reviewed statement/assets/version/presentation/scoped response and fitting direction/functional/rendered checks/dependencies. An unseen/private/text-only preview, approved heading/stack or partial v1 reply cannot settle unreviewed remainder/v2; missing visual access/agreement stays provisional with question/owner/action, while unrelated authorized work continues. Load `ui-ux-design` early for material exploration; prepare a separate design child only when independent acceptance/dependency warrants it, then checkpoint its named revision before own investigator entry. Tiny in-direction corrections use concise sourced acceptance/focused checks, not token alternatives/style microapproval; material direction cannot be tiny by file count. Review is not child authorization; material changes still follow D/revision/checkpoint gates.
3. Check whether their combined intended result advances the parent's criteria; record overlap or dependencies. Give separate production workers disjoint owned outputs if parallel work is intended. Put preparation evidence in the parent's relationships/evidence section, **not** in its append-only `Checkpoints` section; that section contains only actual user approvals.
4. Return only **ready, source-checked** child IDs/revisions as a bounded group for the orchestrator to present to the user; report provisional children and blocking questions separately, not as checkpoint requests. The parent may advance by preparing children; **do not enter them** before the parent records each named revision's actual user approval. Root or sibling approval does not cover a child, and verified slices do not automatically verify the parent. Small existing-code issues or non-software work may remain direct approved leaves without these product stages **only with a current justified semantic leaf in Work split** and adequate current requirements/coverage and actual scope agreement for their delivery; uncertainty about splitting is not that justification.

**Output:** draft child briefs, parent child links when sole writer, attempt report, compact receipt per `.agents/workflow/protocol.md`.

**Stop/escalate:** parent is unauthorized, child scope conflicts with parent/inherited decision, or work cannot be bounded yet. Return upward rather than inventing requirements.
