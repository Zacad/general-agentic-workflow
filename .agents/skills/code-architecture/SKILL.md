# Case-driven software architecture

**Trigger:** Either (a) a nontrivial new software product has no app code yet and needs a product-level architecture/test-strategy comparison from reviewable product requirements, or (b) a named existing-code change or review needs a justified choice of boundaries, dependencies or abstractions. For (a), load `references/greenfield-product.md` on demand; for (b), follow the source-first steps below without requiring a PRD, platform matrix or pre-code reference for a small issue. Non-software requests do not trigger this specialist skill. This is reasoning alongside `critical-reasoning` and `choose-approach` (and `inspect-codebase` for existing code); follow the assigned role, approved unit, ownership and lifecycle protocol separately. Do not treat this skill as authority to implement.

**Inputs:** bounded question, unit/revision/checkpoint and owned output/report paths. For a pre-code product: user's actual request, available PRD or brief with source/status for requested, proposed, agreed and open statements (use `product-requirements` when substantive discovery is needed), scenarios and quality constraints; an absent or pending PRD is not an approved specification. For existing code: actual relevant code and adjacent tests; requirements, use cases, integration contracts, constraints and observed change history (or explicit absence); target runtime/language versions and available capabilities. Ask which stack(s) matter if a stack-dependent choice cannot be made; continue stack-independent analysis meanwhile.

**Procedure:**
0. Select the branch from actual evidence: if no app code exists for a nontrivial new software product, load `references/greenfield-product.md` and use its product-flow, full-option and test-strategy comparison; do not demand nonexistent executable paths. A draft PRD or unanswered choice permits conditional analysis, not an approved platform. Otherwise use steps 1–5 below for actual code; absence of an unrelated future platform choice does not block a bounded existing-code comparison.
1. Read the relevant executable paths and tests, and trace real callers, data flow, error behavior, dependencies and ownership. Check requirements and use cases against observed behavior, and inspect language/library capabilities in the versions actually used before citing them as design reasons. Label observations, sourced requirements, assumptions and unknown future pressures distinctly; don't infer a product roadmap from a toy test.
2. State the decision horizon: which known changes must this design accommodate? Identify independently changing rules, consumers and integration boundaries with line/test/requirement evidence, and distinguish confirmed needs from hypothetical extensibility. Look for contrary evidence (shared behavior, tiny scope, fixed call sites, expensive migration or untested error handling).
3. Compare at least two implementable designs for the *same* named cases. Include a small concrete/reversible baseline (even if the current implementation is flawed); consider extraction at an observed seam and an interface/registry only where a concrete consumer, independently varying implementation, substitution test or integration contract earns it. Describe what files/callers change, behavioral parity, testing and migration cost, new indirection and failure modes for each. SOLID may suggest separating genuinely different responsibilities or inverting a changing dependency; KISS penalizes needless moving parts; YAGNI penalizes speculative variants. None is a veto: weigh their conflicting predictions against actual change pressures and tests.
4. Recommend the smallest design that satisfies confirmed constraints; distinguish a local reversible choice from a consequential decision requiring the workflow's decision/checkpoint process. Give rejected options a fair best case, cite counterevidence and uncertainty, and name observable triggers for revisiting (e.g. a second independent caller, divergent rules or measured duplication). If evidence is insufficient, specify the minimum check needed instead of inventing a general rule.
5. Check the comparison against source lines, tests and constraints; run focused read-only or authorized checks where useful. Record failures and untested claims, rather than presenting a proposed design as implemented or verified.

**Output:** In the assigned artifact/report: decision question and evidence map (paths/lines/tests where code exists; PRD/brief sources and statuses before code; versions and limits where relevant); alternatives with concrete effects and tradeoffs; provisional recommendation or blocking user choice, rationale, counterevidence, uncertainty, review triggers and focused check results. For a pre-code product, follow the reference's explicit affected unit/revision and checkpoint-owner handoff for consequential proposals. Use existing workflow skills for implementation or formal decisions; do not duplicate their records.

**Testing comparison/review (both branches):** For material testing commitments, consume current sourced normal/error/recovery/quality scenarios and applicable specifically reviewed strategy or use `choose-approach`'s conditional method; the pre-code reference elaborates it alongside the full architecture options and evidence ladder. On existing code, tie methods and expected observables to actual executable/test paths and changed failure surfaces; do not force greenfield platform discovery. Compare at least two implementable same-driver testing strategies, not just design options or libraries; map critical coverage/evidence/limits, version-primary sources and separately observed prerequisites. Assign a separately owned concise user artifact for actual orchestration presentation and retain exact presented version/statements, actual response and scoped applicability before affected material commitments. Stored architecture or stack approval is not strategy review. Reuse adequate specifically reviewed unchanged input; a tiny exact issue retains meaningful focused regression/limits without token alternatives. Follow protocol affected-only readiness and material D/revision gates; feasible planned-unrun tests are not executed evidence or an automatic pre-code implementation blocker.

**Optional stack guidance:** Load a stack-specific reference only if the selected case needs one; cite authoritative, dated/version-scoped sources, compatibility and limitations in that reference. No profile is implied by this stack-independent skill. Verify the local runtime/capability for each case instead of extrapolating across languages.

**Stop/escalate:** On the existing-code route, missing relevant code, essential requirements or integration contract prevents a defensible recommendation; on the pre-code route, an essential unanswered or declined product choice blocks only dependent direction/build, not independent conditional comparison. Escalate when unspecified stack is material, ownership or authorization is unclear, or a proposed change exceeds the unit's boundaries or conflicts with an approved inherited decision. Report the precise gap and affected unit/revision; ask the checkpoint owner for actual user resolution before affected work advances.
