# Pre-code architecture for a nontrivial software product

Load only from the `code-architecture` pre-code branch. This is a comparison method, not an approved stack, implementation plan or permission to build. Use `product-requirements` to elicit/review product behavior and `choose-approach` to distinguish routine reversible tools from consequential decisions. Use the actual unit brief/checkpoint and applicable decisions for authority.

## 1. Ground the comparison in flows and status

- Make a compact evidence table: statement → exact user quote/PRD or brief path + section/checkpoint → status (`requested`, sourced `constraint`, `proposed`, specifically user-reviewed `agreed`, `excluded` with authority, or `open/unknown`) → architecture/test implication. A root checkpoint agrees only what that root actually specified. No review, silence or declined answer converts a proposal into agreement. If no PRD exists, use the request verbatim and mark every added assumption proposed; ask the few questions that could change the platform or product outcome. Continue comparing conditional options where possible.
- Choose the **same** representative flows and exceptions for all options: actor/identity → entry → action/confirmation → persistence/reload/recovery → terminal outcome, plus offline/blocked-storage or failed-network branch. For a Polish checkers request, *ask* about ruleset, endings (resign/pass/draw and no-move), shared versus same-device play, saving/history/identity, recovery, devices and accessibility; do not assume the answers. For a clinic booking request, ask who can book/cancel, who sees patient data, how a slot is reserved, what happens after uncertain submit/retry, cancellation and recovery. Distinguish user-visible behavior from implementation.
- Turn each sourced/conditional flow into quality drivers with observable checks: operation and recurring cost; identity, security and privacy/data ownership; durability, recovery and acceptable loss; offline behavior and latency/performance; accessibility, keyboard/pointer and supported device/viewport; plus domain-specific constraints. Rank drivers by evidence/status, note what could disqualify an option, and leave numerical targets as questions unless supplied. Do not infer a cross-stack rule from a single trial.

## 2. Compare at least two complete solution options against those flows

For *each* option state client execution, state owner/storage and API/sync boundary, identity/trust boundary, hosting/deployment versus local development serving, runtime/build/test tooling, migration and failure/recovery path. Use the same driver table to compare operational work/cost; privacy/security/identity; durability/recovery/quota; offline/latency; accessibility/device support. Cite sourced constraints, mark conditional estimates as estimates, describe a best case and downside, and give a trigger to revisit. Options below are candidates **only** for browser products; replace them when the actual product constraints warrant another platform.

| Candidate full path | Operations/cost; identity/privacy/security | Durability/recovery/quota; offline/performance | Accessibility/devices and failure tradeoff |
| --- | --- | --- | --- |
| A. Browser UI + client-only state in `localStorage`; static files deployed if access by URL is required; no product API or accounts. Native browser modules or a replaceable build tool can package the client. A local static server used for development serves files only. | Small infrastructure footprint; maintenance of UI/data format still needed. Names are not authenticated identities; origin/profile-local data can be read by others using that browser profile; no automatic cross-device sharing. Hosting static assets is a separate product access question. | String-only, synchronous writes and limited quota; validate/version records and surface denied/quota writes; device loss, user deletion and private mode lose records without a separately agreed export/backup path. Can run interactions offline *after assets are available*; offline first load/reload requires an explicitly designed asset-cache/install path. Watch main-thread delays and competing tabs. | Browser semantics, focus, target sizes and responsive layout must be tested; desktop success does not establish narrow/touch success. Suitable only if same-profile scope and loss risk are acceptable; recovery cannot be promised without another mechanism. |
| B. Browser UI + client-only IndexedDB (versioned records, transactions), with optional explicit export/import if user agrees; static deployment and local development server distinguished as above; no product API/accounts. | Still low server operations, but schema migration, upgrades and error paths cost more. Profile-local data remain unauthenticated and visible to users of that profile; sharing/export adds privacy handling. | Asynchronous structured records/indexes and multi-record transactions suit growing history; browser quota, blocked/failed transactions, corruption, user deletion and profile loss remain. Test migrations and write acknowledgement. Offline first load still depends on asset delivery; IndexedDB alone does not cache app assets. | Same rendered/keyboard/touch obligations as A; test loading, pending-write and storage failure feedback. Prefer only if history size/atomicity or query needs justify complexity; it does **not** give cross-device durability. |
| C. Browser UI + hosted application API and durable server store, optionally client cache/offline sync; deployed service is a distinct operating component. | Recurring hosting/monitoring/backup/migration cost. If shared or sensitive data matter, define authenticated identities, authorization, transport protection, retention and access boundaries; names alone are not identities. | Central backup/restore and cross-device sync become possible only if designed and checked; network outages, unknown success after retry, concurrency/conflicts and server loss add failure paths. Offline writes require explicit queue/conflict policy; online calls add latency. | Client still needs browser/viewport/assistive inspection; pending/failed/retried states and keyboard flows need observable status. May fit genuinely shared/strongly retained records, but do not install a backend as a default. |

Compare A **and** B explicitly even if both are client-only; when shared identity, central recovery or synchronization is material **or still unanswered**, also compare C conditionally now, rather than deferring the comparison until the user answers. A and B differ in storage/API failure surfaces, not in their ability to deliver authenticated shared state. An answered local-only constraint can rule C out for that product; it does not automatically approve A over B. For a clinic, test whether unauthenticated single-device bookings can meet slot ownership, privacy and uncertain confirmation: if not, record why a hosted/identity option is conditionally stronger, and ask for approval before dependent work. Runtime of delivered code (e.g. browser JS), build/test runner (e.g. Node or Deno) and a local development/static-file server are separate; **a Deno local server serving assets is not a deployed application backend**. Do not select Deno, a framework, deployment or browser persistence simply because one tool was installed in an earlier project.

## 3. Compare feasible verification, not just libraries

For each candidate give an evidence ladder with actual prerequisites and gaps; select only checks executable in the target environment and mark the rest pending. Target the same normal, exception and recovery flows above, plus accessibility/device constraints.

Alongside that ladder, compare **at least two implementable testing strategies for the same sourced flows/quality risks**, following `choose-approach`'s conditional method. Architecture A/B/C and different runner names are not testing alternatives. For a browser product, candidates might be:

| Same-case testing strategy (conditional, not a default) | Confidence / failure surfaces exposed and missed | Setup, maintenance, human/cost and feedback tradeoff / prerequisites |
| --- | --- | --- |
| Risk-weighted layered automation: deterministic domain/state fixtures + real critical storage/API boundary checks + targeted served real-browser submit/save/finish/retry/reload/failure regressions; relevant manual/assistive/device observations supplement automation. | Repeatable exercised-rule and boundary confidence, with rendered regression checks on named engines/states. Controlled faults expose handling; mocks cannot prove actual storage/service, selected browser cases miss untested engines/assistive states, and isolated restore does not prove production durability or user success. | More initial fixture/data/service/browser isolation and selector/fault maintenance; short deterministic rule feedback, slower potentially timing-flaky boundary/browser feedback; less repeated human flow work, still specialist observations. Needs compatible runner/browser binaries/OS dependencies, real store/service where claimed, and relevant device/assistive setup. |
| Deterministic domain/state + real critical boundary automation, with reproducible recorded manual real-browser release flows for **the same** normal, failure, uncertain retry/reload and recovery cases and relevant device/assistive observations. | Direct rendered/status/focus observations and actual boundary confidence with less UI automation. Weaker frequent UI-regression/race exploration and more operator omission/variability; real boundary concurrency tests still needed where relevant. Untested engines, production loss and learner/user success remain unproved. | Less selector/automation setup and maintenance, more recurring human checklist/retest effort and slower release feedback. Domain checks stay deterministic; human timing is variable. Requires reproducible states, agreed outcomes and actual browser/service/device/assistive availability, not merely a checklist file. |

These are qualitative tradeoffs, **not measured benchmarks**. Recommend from actual risk, release/feedback needs, available human effort, cost/support constraints and feasible prerequisites; give both a fair best case and revisit trigger. Neither excuses missing material coverage. If required browser/device/service capacity is absent, both retain that gap; a hosted service's cost/privacy/support effects require applicable authority, not silent adoption. Product response latency is separate from test-feedback latency. Keep unanswered targets/behavior conditional rather than inventing guarantees or reducing support.

For every material scenario/acceptance/quality statement, retain this concrete coverage trace:

`statement/scenario → exact source/status/current review applicability → normal/error/recovery risk → concrete input/starting state + method/check level + expected observable → expected evidence and limits → actual version-scoped primary documentation + runtime/service/device prerequisites and separately observed local capability/how checked → planned-unrun / blocked-prerequisite / separate exact executed target/environment/method/result link → affected dependency, open owner/action, deferred disposition or actual authorized exclusion basis`.

For example, **only if sourced/agreed**: available slot + permitted actor → submit → agreed acknowledgement/retained record; accepted write + lost response → retry/reload → agreed uncertain/recovered status and record count; denied/quota/failed transaction → explicit failure + permitted recovery → agreed prior/retained state after reload. Specify concrete fixture state and observable status/record/invariant, not just “test recovery.” Domain fixtures check agreed rules; a controlled real-boundary check inspects actual records/acknowledgement; a served-browser check observes retry/reload/focus/status. Mock response loss alone cannot prove real idempotency; a single-record expectation needs an agreed retry policy. Trace relevant accessibility/device, security/privacy/identity, durability/retention/recovery, operations/effort/cost and performance risks across as many checks as needed. Missing behavior or tooling leaves owner/next action and affected claim visible, never omission-as-exclusion.

| Level | Feasible check and prerequisites | What it establishes / cannot establish |
| --- | --- | --- |
| Unit/domain/state | Pure state transition fixtures for game endings, counters, reload encoding; or booking slot/cancel/duplicate-retry rules. Requires runnable compatible language/test runner and agreed expected behavior. | Rules and state invariants in fixtures; not actual browser storage, server races, rendering or user interaction. |
| Integration/storage/API | Real browser storage or isolated storage adapter with migration, quota/unavailable, failed transaction and recovery; for hosted option, API + store with authentication/authorization, idempotency/concurrency, ambiguous response and backup/restore checks. Requires provisioned store/service for claims about it; mocks isolate application behavior only. | Boundary contracts/failure handling at the level actually exercised; a mocked API does not prove deployed API/network/real-browser behavior. |
| Real browser E2E | Launch the served UI in an actual compatible browser with Playwright or equivalent and supported runner + matching browser binaries/OS dependencies; confirm install/network availability or provision an existing compatible browser. Exercise pointer and keyboard, reload/save/finish or book/retry/cancel, storage/network failure, desktop and narrow viewport. For hosted flows use a real test service where its contract is claimed. | Demonstrates the tested browser path/viewport, not every browser, production durability, full accessibility or usability. HTTP 200, DOM simulation, jsdom and mocks are **not** browser E2E. If tooling unavailable, perform documented manual real-browser flows if a browser exists; otherwise mark browser outcome unchecked and name compatible runner/browser installation or a provisioned environment as next step. Do not assume a Deno runner can execute a Node Playwright suite without validation. |
| Manual rendered/accessibility | In a real browser, inspect keyboard order, focus visibility, status announcements with appropriate assistive-tech where possible, pointer/touch usability, desktop/narrow reflow, overflow and measured geometry with viewport/tolerance (e.g. board row/column/cell equal dimensions where required, or booking-grid alignment). Requires browser/device or emulator and explicit expected invariant. | Finds observed UI failures only; viewport simulation is not a physical-device test, automated contrast or width-only checks do not prove rendered geometry or full accessibility. |

Record browser version, runner version/compatibility, OS and exactly which flows ran; a test plan is not execution evidence. Check relevant platform and test-runner primary docs at the versions in use before a source-specific recommendation. Illustrative, bounded references: MDN [localStorage](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage) (last modified 2026-07-28: origin-scoped, string-only and private-mode behavior), [Web Storage API overview](https://developer.mozilla.org/en-US/docs/Web/API/Web_Storage_API) (2025-02-22: `localStorage` set/get/remove operations are synchronous and can block other JavaScript), [IndexedDB](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API) (2025-04-03: asynchronous indexed transactions), [storage quotas/eviction](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria) (2026-01-05: browser-specific policies and deletion), and Playwright Node [installation](https://playwright.dev/docs/intro), [browsers](https://playwright.dev/docs/browsers) (online docs inspected 2026-10-01: compatible runner, browser binaries and dependencies required). These support candidate properties, not a guaranteed quota, supported stack or local installation; recheck target versions/browsers.

For an actual recommendation, match primary sources to the target release/version (or date online docs and state version uncertainty), and separately record observed local versions, compatibility and launch/service/device capability with the method used. Documentation/binary presence does not establish a successful launch or product test. Missing/incompatible runner, browser/OS dependencies, service, assistive/device or reconstruction setup remains pending with owner/next check; no automatic installation/provisioning. Select feasible planned checks conditionally when implementation is still future: sufficiently settled agreed prerequisites/strategy may authorize build with tests **planned-unrun**, not falsely executed or automatically blocked solely because no app exists yet. Build/typecheck/HTTP/mocks and plan approval cannot establish actual browser/storage/recovery/learning evidence. An independent verifier remains free to add necessary failure-detecting checks beyond the plan.

## 4. Recommend provisionally and hand off authority

Assign a worker a separately owned **concise user-facing comparison/review artifact**, distinct from detailed report and compact receipt: sourced drivers, meaningful same-case strategy alternatives/recommendation/conditions, critical coverage/expected evidence/limits, prerequisites, prioritized questions and affected readiness. Have the orchestrator actually read/relay it through the full discussion/answer-artifact route before affected material commitments. Retain the stable version/content or individually identified exact statements presented, path/version plus hash or retained copy where useful, actual presentation reference/scope, actual response/quote/reference and statement-specific applicability through owned artifacts and the assigned writer. A stored unseen architecture/strategy, generic architecture approval or stack/storage reply does not review unseen testing clauses. Separate adequacy, presentation, agreement and dependent readiness: partial/pending/declined/conflicting review leaves the remainder truthful; v1 review covers no v2 additions or future defaults. An authorized draft/open review handoff may finish without claiming dependent build ready.

Validate/reuse adequate specifically reviewed unchanged strategy with exact prior presented scope/version/response, adding only changed/missing gaps without ceremony. Tiny focused existing issues use the choice method's concise approved acceptance/regression/limits route, not this full greenfield comparison. Artifacts/review remain evidence, not child authorization: named current-revision checkpoint still precedes own distinct investigator. Material platform/support/effort/cost/quality/acceptance/outcome or inherited changes follow applicable D/revision/checkpoint gates, pausing only affected dependencies. Routine local tools remain delegated as below.

Give the strongest option **under each still-open material constraint** or state which answer blocks a preference; explain rejected options fairly, explicit uncertainty, evidence required, and observable triggers (e.g. cross-device sharing, actual history size, quota errors, conflict on retries). Never say a technical direction is approved from a draft PRD or this comparison. For each material persistence/identity/hosting/platform choice, name **affected unit ID@revision** from the real brief (or `ID/revision to assign` when there is none), dependent work paused, and **owner/next action: orchestrator requests actual user review and records the applicable root checkpoint, named parent checkpoint for a child, or revised scope/decision checkpoint where materially changed**. If existing scope already authorizes the unchanged choice, cite that checkpoint; no new checkpoint for a routine answer within scope. Use `choose-approach` for consequential proposed decisions and protocol authority; do not create or approve a D-record without ownership. Keep replaceable local runner, bundler or static development server delegated within the approved constraints. Escalate a declined or missing answer only where it prevents affected advancement; continue independent authorized analysis.
