# Start existing work

**Inputs:** request/issue, workspace rules, relevant existing artifacts, candidate parent/root, assigned paths; applicable own-unit investigator report set and assigned planner integration basis for substantive framing/preparation (initial independent root: allocate ID and framing basis first).

Apply the protocol's same-unit assignment/consumption contract wherever the framing steps below refer to an investigator/report: compare one, concurrent independent and staged dependent questions; actually read applicable primary reports/material sources. One assigned planner integrates union coverage, conflicts/dependencies and whole-unit sizing including no-split from scoped contributions, not summary assertions or redundant all-unit packets. Link reports/integration and selective retained/revalidated/replaced evidence in existing Relationships; affected gaps need owner/action and renewal, with full discussion fail-closed and selected-level readiness preserved. Parent research remains parent preparation; an entered child still needs exact current-revision authority and distinct own-unit investigation.

**Procedure:**
   **Visual intake:** distinguish material new UI/changed direction/substantial review from adequate unchanged reviewed direction/design-system reuse or a tiny in-direction label/focus/semantic-role correction. During authorized framing/preparation, validate desired quality/taste, audience/tasks/setting/platform/assets/references and actual source/status; ask a few material questions and load `ui-ux-design` before direction production. Follow the protocol's visual-review gate: inspect exact assets/version/presentation/actual response/current states/constraints before reuse, add only gaps, and use concise acceptance/focused checks for tiny corrections. Root/stack/brand labels are not review, and file count cannot make a material new direction tiny. Missing brand may be a proposed contextual default for real visual review; name material gaps' question/owner/action and pause only affected dependencies.

1. Do bounded intake to identify the requested outcome and locate matching existing units/authority; leave substantive research and framing until the evidence gate below. The assigned investigator reads relevant context, constraints, current behavior and decisions, using `inspect-codebase` for software when appropriate.
2. Determine whether this is a *new root* for a bounded issue or a child of an existing unit. If a child, consume/check the authorized parent's linked investigator report and draft as **parent preparation**; do not enter the child's investigation/production before its named current-revision checkpoint. If an independent root, invoke a distinct investigator on bounded framing inputs with `investigate-unit`, then have a separate assigned writer consume/check its report; no initial brief/checkpoint is required. Follow protocol applicability/revalidation; parent evidence or self-research cannot substitute for new-unit entry.
3. With assigned ownership, draft a brief from `.agents/workflow/unit.md`, including evidence, boundaries, meaningful criteria, dependencies, parent link, and initial next action. Link the root's consumed framing report; a prepared child cites parent research as input and says its own investigator is not invoked, first after authorization. Reuse existing requirements rather than duplicating or contradicting them, validating current substantive adequacy and actual specific review applicability per protocol; an “approved” heading or generic root is insufficient. Add only missing/changed gaps. Set revision 1 and `ready` only when the current material scope/sizing is settled enough.
   For substantial missing or materially changing nonsoftware requirements, use `endeavor-requirements` within the authorized scope to discover/review full material dimensions, expected content/depth, exceptions and constraints before dependent delivery. Broad unresolved scope normally warrants a separately reviewable specification/coverage artifact; a requirements child is conditional on independent acceptance/dependency value, prepared as parent work and checkpointed before own entry. Trace each material acceptance item to sufficiently agreed current statements or applicable approved brief/D authority and suitable checks/dependency readiness. Keep gaps, pending/partial/declined review and provisional later horizons visible with owner/action. For a tiny exact issue, concise sourced coverage/readiness in the brief/report and a focused check suffice; do not force a specification hierarchy or software architecture onto nonsoftware work.
   For either branch, write mandatory `Work split` per protocol using actual existing requirements and consumed root/parent investigation: compare plausible semantic vectors including no-split, explain selection, and give current proposed child outcomes/dependencies/readiness/contribution/check horizons or the unit-specific single-horizon leaf and why finer splitting adds coupling rather than useful acceptance/retry. Shared artifacts do not erase independent outcomes. Open sizing remains provisional with a named question, evidence, owner and next action; prepare only the next useful horizon, with child entry/investigator still pending its named checkpoint.
   For either branch, the sole writer fills the mandatory `Decision log` per protocol from actual user/reviewed inputs, individually identified applicable parent/protocol/D positions and settled local preparation/approach/check/dependency choices, with status, scope, alternatives, concise rationale and source/actual authority. A generic ancestor link is not coverage. Separate proposals/open alternatives; absent historical alternatives/rationale are `unknown/not recorded`, new comparisons/inferences labeled. Check meaningful completeness before claiming the draft current; a prepared-child log does not assert child investigation or approval.
4. Return the brief for explicit approval of its named unit/revision. Record uncertainties that might require investigation later.

   Lead user-visible scope/checkpoint artifacts with outcome names/context before IDs/revisions. Validate the existing selected-group/coordinating Work split/Relationships and current wave when resuming; an isolated ready leaf is insufficient. For new broad scope expose preliminary structure questions during framing, then after adequate requirements/appropriate structure show the broad high-level horizon and explicitly choose a bounded delivery group with the user. Use useful proposed project-specific taxonomy, not fixed levels or sizing proof. Address relevant siblings in waves before deeper preparation/entry under their own named checkpoints/investigations; preserve justified uneven depth and independently acceptable modules/infrastructure as well as slices. Before dependent delivery every selected path needs evidenced justified-leaf readiness or retained deferred/blocked reason, owner/action, dependency impact and reconsideration basis. Discovery/requirements/structure/preparation outputs establishing readiness are exempt under their own authority. Record through existing Work split/Relationships with one coordinating authority, no whole-project expansion or tiny-task bureaucracy; changed requirements reopen affected readiness and material authority gates only.

**Output:** bounded root or child brief and attempt report; compact receipt per `.agents/workflow/protocol.md`.

**Stop/escalate:** ambiguous parent, overlapping existing unit, uncertain project rule, or conflicting inherited choice. Do not silently select a root or bypass the child checkpoint.
