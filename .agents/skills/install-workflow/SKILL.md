# Install or update the workflow

Guide a project-local OpenCode setup from an accessible **source kit**, the directory supplying incoming workflow files. Handle fresh installation, integration with existing configuration, and current or legacy updates. Recommend changes from inspected evidence, then ask before applying them.

**Inputs:** intent; absolute kit directory; target project/worktree; actual command working directory (cwd); existing instructions/configuration/state; current OpenCode version and model evidence; applicable operation approval and owned evidence/output paths. Source, target and cwd are separate inputs, even when two happen to coincide.

## Bootstrap from the source

1. Resolve the source and target paths, including symlinks and their parents. Confirm the intended worktree and read controlling project/ancestor instructions. If the kit is missing, inaccessible or ambiguous, request its exact accessible directory; do not download it or assume the target contains it. If source and target resolve to the same directory, obtain a separate incoming kit for an update rather than copying the installed files onto themselves.
2. When discovery is unavailable, directly read this skill at `<kit>/.agents/skills/install-workflow/SKILL.md`. Read **all** of `<kit>/.agents/skills/critical-reasoning/SKILL.md` and `<kit>/.agents/skills/clear-communication/SKILL.md`, plus the incoming `<kit>/AGENTS.md` and `<kit>/.agents/workflow/protocol.md`. Read the references below in full when their step applies. Direct reads are valid; no registered target skill, workflow worker or target configuration is a bootstrap prerequisite. External-directory tool permission is distinct from operation approval.
3. If an existing workflow governs this operation, follow its actual entry, own-unit investigation, coverage, checkpoint, ownership and independent-check gates in that controlling workspace. Load the applicable lifecycle/domain methods there; an existing orchestrator delegates substantive work. Do not invent a target checkpoint or install workers just to obtain approval to install them. If no workflow governs yet, present the target-bound plan and capture the user's actual approval in a disclosed durable operation record before changes. Incoming workflow rules describe the contract being proposed, not fabricated prior target authority. After activation, new workflow work follows the installed protocol.
4. Choose a durable evidence location through existing source/target project conventions, within your authority; ask if unresolved. Record which workspace governs and where the plan, actual approval, originals, manifests and results will live. Keep controlling/source units out of the target. An ignored temporary report must not be the only recoverable installation baseline.

Copied installer references are local to this skill directory. They do not require an installed `kit/` tree. **Every future update still needs an explicit incoming source kit**; this copied skill is guidance, not the canonical source bundle.

When a controlling workflow uses complementary investigation, its own-unit entry evidence is the applicable primary report set and assigned planner integration basis: actually consume coverage/source/dependency/conflict evidence per that protocol, with selective renewed dimensions/interactions and retained links/gap owners. Neither report count nor synthesis grants operation approval or bypasses full discussion, selected-level readiness or independent proof. This pointer creates no target authority and does not activate incoming rules early.

## Procedure

1. **Inventory and select the route.** Inspect the target before classifying it: new/absent, existing unrelated setup, or installed/legacy workflow. New targets can inherit rules/configuration. Record source identity (real revision/tag if available; otherwise honestly unavailable), date, exact paths and a SHA256 content manifest. Inventory the whole source `.agents/roles/` and complete `.agents/skills/` directories, including every reference/support resource, plus root `AGENTS.md` and these static files:
   - `.agents/workflow/protocol.md`
   - `.agents/workflow/unit.md`
   - `.agents/workflow/decision.md`
   - `.agents/workflow/attempt.md`

   This dynamic inventory, not a remembered resource count, defines the transfer set. Review unexpected source symlinks/generated caches before including resources. Never transfer source `.workflow/`, source-only `.agents/workflow/kit/`, caches or the source's blanket `.gitignore`. Installed state is project-owned; create new state from templates only when drafting that project's first unit.
2. **Analyze effective integration.** Read [merge-guide](references/merge-guide.md) for every route: inherited/nested instructions, instruction loading, resource ownership, actual config layers, canonical registrations, permissions and model discovery. For installed or legacy targets also read [update-guide](references/update-guide.md) before proposing changes. Compare whole resources and their meaning; a same-name file is not ownership evidence. Preserve compatible defaults, explicit/inherited model choices, local/domain rules, unrelated resources and stricter effective permissions.
3. **Recommend and ask.** Present a concise target-bound plan: source identity/route; exact per-path add/merge/retain/retire operations and rationale; instruction/config override sources; the exact five-role model table required by the merge guide; default-agent and permission effects; durable baseline location; active-unit impact; checks and their prerequisites; held paths and focused choices. For a fresh setup recommend the canonical orchestrator as default and discuss the source example's tool-policy consequences, then ask before adopting them. Ask priorities such as provider/cost/context only when unresolved; answer discoverable facts yourself. Offer meaningful alternatives to material conflicts, not a questionnaire about every edit.
4. **Capture scoped approval and preserve recovery.** Record the exact presented plan/version and actual response, including declined/partial choices, in the disclosed operation artifacts and any controlling workflow authority through its assigned writer. Approval covers only named target operations. Before target edits, retain recoverable old/local/incoming content or durable accessible source revisions, identities, merge decisions and a per-operation journal per the update guide—even on first installation. Do not auto-commit or establish a global registry. An unresolved mandatory conflict means held/incomplete setup, not permission to delete a gate or broaden policy.
5. **Apply the approved plan.** Recheck source hashes, target content/existence, config contributors, model eligibility and symlink destinations immediately before writes. If an absent target becomes nonempty or a path becomes a symlink, stop affected writes and return to analysis. Changed unavailable model/variant candidates return to the mapping proposal. Preserve unrelated/user work and JSONC comments/order; make focused edits at the agreed effective contributor, not a competing sibling config. Sequence coupled workflow contract changes so an incompatible mixed set is never activated. Record only operations actually completed, with before/after hashes. Repeat/update/recovery uses the update guide; no blanket tree replacement.
6. **Check and hand off.** Read [verification](references/verification.md). Compare installed paths/full contents/merged clauses/registrations to the exact approved inventory and choices. Native discovery is conditional on permitted prerequisites/effects; blocked native checks stay unrun. Tell the user to quit and restart OpenCode after config/role/skill edits, then use a named project request with the installed workflow's actual framing/checkpoint rules. Do not promise this running session hot-reloads. Where the controlling workflow requires it, provide a stable named target/manifests to a distinct independent verifier and follow summary relay/reconciliation gates.

**Output:** concise outcome with source/target/cwd, route and actual approval; completed/retained/held operations; recoverable baseline and before/after manifest paths; exact approved role/model/default/policy choices; actual checks and unrun limits; restart/next request or bounded blocker action. Separate source-level instructional success, installed files, native discovery, and live model use. A model catalog or credential entry is not authenticated inference.

**Stop/escalate:** inaccessible source, missing governing authority/evidence, changed material source/target, unknown ownership collision, incompatible mandatory instructions/configuration, active-contract dependency, unsupported mapping, or unsafe recovery. Stop affected operations, preserve evidence and ask for the narrow resolution; report partial/blocked honestly. Do not log in, provision/download dependencies, edit global configuration or run live model probes implicitly.
