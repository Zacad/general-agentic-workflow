# Merge instructions, resources and OpenCode configuration

Use this guide during fresh setup as well as existing integration. The aim is a compatible **effective setup**—the instructions, prompts and permissions OpenCode will actually use—not merely preserved files. Keep the operation's source/target/cwd and approval from [the entry skill](../SKILL.md) explicit.

## Instructions and portable resources

Read root, ancestor and applicable nested `AGENTS.md`, existing `.agents`, `CLAUDE.md`/other supported fallbacks, and configured `instructions` sources. Identify each rule's scope and purpose before adding kit rules. In the checked OpenCode v1.18.34 behavior, adding AGENTS can suppress CLAUDE fallback: retaining CLAUDE bytes does not preserve its former effect. Propose a deliberate integration of required clauses or a supported explicit instruction inclusion preserving scope; avoid duplicated loads and changing nested rules into unconditional global guidance. A Markdown file mention is not an automatic recursive load.

Compare incoming AGENTS/protocol/roles/common skills with local constraints. Retain domain rules such as a required project test command and stricter tool policy. Deduplicate semantically equivalent workflow clauses rather than appending another managed block. Read existing managed sections and ownership evidence; do not presume their names make them replaceable. Explain incompatible clauses, for example a mandatory no-delegation rule versus required distinct workers, or a no-write policy versus workers' attempt reports. Ask the user for a scoped compatible resolution or hold installation incomplete. Do not strip investigation/checkpoint/independent-check requirements, silently loosen policy, or call retaining two contradictory rules a successful merge.

Inventory every incoming role and whole skill directory, including references and support resources. For each target collision inspect its full content, local references, provenance and actual purpose:

| Collision | Action before an approved change |
| --- | --- |
| Known unedited kit resource | Compare incoming changes and dependencies; propose refresh, using recoverable baseline evidence. |
| Edited kit role/skill/static file | Compare old base, current local and incoming meaning per [update-guide](update-guide.md); retain compatible additions and resolve conflicting contracts explicitly. |
| Same name, unrelated or unknown ownership | Preserve it; propose a reviewed integration or relocation with all live references checked. No presumption of kit ownership or automatic rename. |
| Duplicate skill across project/global/configured locations | Inspect definitions, permission filters and actual loaded location/body when feasible. Resolve the collision; do not rely on deterministic winning-location precedence or a discovery count. |

Keep canonical role names by default: protocol and task policies refer to them. Inspect actual intent of a same-name OpenCode agent rather than overwriting it. Any proposed alias requires a complete, explicitly reviewed compatible mapping of current protocol/roles/task references/registrations and checks; a convenient rename alone cannot complete this kit's integration. Keep unrelated `.agents` resources and existing project `.workflow` state. Only the four static files named in the entry skill are portable workflow statics; source-only examples/docs/fixtures are references, not transfer payload.

## Find configuration contributors

Record OpenCode version, target cwd/worktree and installed help before choosing commands. Inspect existing `opencode.json` **and** `opencode.jsonc`, ancestor/worktree configuration, `.opencode/opencode.json(c)`, both `.opencode/agent/` and `.opencode/agents/` Markdown definitions, relevant global/directory agent definitions, custom config paths, environment/inline overrides, plugins and managed/organization contributors supported by that version. Identify `OPENCODE_CONFIG`, `OPENCODE_CONFIG_DIR`, `OPENCODE_CONFIG_CONTENT` or project-disabling settings by presence/source and relevant non-secret effects; do not dump secret-bearing environment values. Inventory configured instruction/skill paths and provider filters as well.

Determine which contributor supplies each effective workflow field, including later directory-agent overrides. Inspect accessible inputs locally, preserving secret placeholders; if an external/managed contributor cannot be inspected or safe resolution is unavailable, state the exact unknown/override and hold affected claims. A project edit cannot fix a stronger inaccessible override. This skill does not authorize global or managed edits; propose their required owner/action separately.

Patch the agreed existing contributor in its native JSON/JSONC form. Preserve comments, unrelated providers/agents/plugins/fields, `$schema` and meaningful field order. Do not parse/stringify away comments, perform a universal recursive JSON merge, union every array, or add a competing JSON sibling to evade a conflict. Loader merge rules are field/version-specific. Validate proposed fields against current official schema and matching installed behavior; the built-in `customize-opencode` method may help when available, but is not a bootstrap prerequisite.

### Canonical registration and task contract

Use the actual incoming role bodies, not prompts inferred from agent names. The current canonical mapping is:

| OpenCode name | Mode | Prompt file in target | Task policy |
| --- | --- | --- | --- |
| `workflow-orchestrator` | `primary` | `.agents/roles/orchestrator.md` | Deny `*`, then allow `workflow-investigator`, `workflow-planner`, `workflow-producer`, `workflow-verifier`. |
| `workflow-investigator` | `subagent` | `.agents/roles/investigator.md` | Deny task delegation. |
| `workflow-planner` | `subagent` | `.agents/roles/planner.md` | Deny task delegation. |
| `workflow-producer` | `subagent` | `.agents/roles/producer.md` | Deny task delegation. |
| `workflow-verifier` | `subagent` | `.agents/roles/verifier.md` | Deny task delegation. |

`agent` is a configuration object keyed by these names. A root config can use `prompt: "{file:./.agents/roles/producer.md}"`; when the declaring config is `<target>/.opencode/opencode.json`, the corresponding path is `"{file:../.agents/roles/producer.md}"`. Resolve file substitutions relative to **the declaring configuration**, not the command cwd or source example. Check all five exact paths and complete prompt bodies. Plain role files are not automatically registered by OpenCode. A chosen `default_agent` must be an enabled, non-hidden primary; preserve a compatible existing default. If it remains another agent, explain how to select `workflow-orchestrator` explicitly.

The source `<kit>/.agents/workflow/kit/opencode.example.json` is a registration **reference**, not a wholesale-copy plan. Its model placeholders must never reach target config. Its per-agent `edit: allow` and `bash: allow` can broaden stricter global policy. Recommend/review their consequences for a fresh target; for all targets use the narrow compatible approved policy, not unconditional example allows. Workers must be able to write their assigned reports and perform required checks under project policy; role ownership limits do not themselves enforce tool-level isolation.

Permission rules use the **last matching rule**, including merged global/per-agent rules. For example, `"bash": {"dangerous *": "deny", "*": "allow"}` allows a matching dangerous command because the later broad rule wins. Preserve ordered semantics, trace relevant operations through all matching rules, and propose corrections only with approval. Per-agent allows can override global denies. In the canonical task mapping the broad deny precedes the four orchestrator allows; worker denial remains effective. Required delegation/report writing denied by a mandatory policy is a material conflict to resolve or hold, not an excuse to copy permissive defaults. Tool permission does not grant workflow scope or checkpoints. Non-interactive runs can reject remaining `ask` permissions; do not broaden policy to manufacture a successful check.

## Recommend exact models from current evidence

A **model variant** is a named settings preset for the same model, not a new model or model ID; for example, a preset may select a reasoning effort if that model/provider supports it. **Model options** are the individual settings actually supported by that provider for the selected model; a variant groups settings under a name. Explain each proposed or retained preset/option's effect using current evidence, and label unknown effects unknown rather than inventing support or behavior.

1. **Establish discovery context and effects.** Record installed version/help, cwd, effective provider setup and enabled/disabled filters. Follow [verification's prerequisites](verification.md#native-prerequisites-and-command-shape) before commands that initialize configuration/providers. Installed v1.18.34 help supports `opencode models --verbose` (optionally a provider argument) and `opencode auth list`; `auth` is an alias of `providers` in that help. Recheck future installed help. Do not refresh/download catalogs, authenticate or probe inference implicitly.
2. **Collect non-secret evidence.** Where permitted, inspect current catalog metadata and redacted auth-list provider/credential-type presence. Do not read credential storage secrets or dump resolved API keys. Metadata such as `tool_call`, reasoning, `limit.context`/output, modalities, status, costs, variants/options is evidence about a candidate, not a universal capability threshold. Preserve units/date/source and label missing fields unknown; catalog costs may differ from the user's actual plan. A filter/plugin/provider restriction can exclude a listed model.
3. **Evaluate existing choices first.** Distinguish deliberate explicit role IDs from omitted models and their effective inheritance. In the checked behavior a worker without `model` inherits its caller primary's model; a primary without one uses the configured selection. Resolve that chain in the actual context, recording the exact effective `provider/model-id` and override source. Preserve suitable existing choices and verified compatible variants/options; do not silently convert inherited to explicit or carry an unsupported variant to a different model.
4. **Compare role fit and alternatives.** Orchestrator/planner need instruction-following, context and reasoning for coordination/choices; investigator needs evidence/tool use and context; producer needs tools/domain production ability; verifier needs evidence/check ability. Compare eligible exact IDs against these needs and known user provider/budget/latency priorities, with evidence limits. One eligible model may fill every role. Independent checking means an actual distinct invocation and owned proof, not a different model family.
5. **Present one current mapping table before writes.** Include every canonical role with exact proposed/effective ID, keep/change and explicit/inherit choice (with inheritance source), verified variant/options or none and their effects with current evidence or explicit unknowns, capability/context/cost/status evidence or unknown, catalog/credential/live-use confidence, fit rationale and an eligible alternative or why none is evidenced. Ask only unresolved priorities/choices. If discovery is blocked, request relevant redacted output or the missing prerequisite; if no eligible model exists, hold the mapping. If an ID is deprecated/unavailable, access fails, or a variant/option is unsupported, return a revised mapping proposal—do not silently substitute.

Keep three claims separate: **catalog candidate**, **configured credential/provider presence**, and **live inference verified** in an exact dated context. The first two do not establish the third. A user may explicitly accept a catalog-only/unknown-capability mapping with its uncertainty recorded; that is configured-but-untested, not verified model access. Confirmed incompatible tool capability or no candidate prevents a complete usable mapping. Any live smoke test needs its own explicit scope/cost approval. Never write example placeholders or claim setup complete because models were listed.
