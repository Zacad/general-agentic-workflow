# Rendered UI checks: use when the outcome depends on spatial layout

Start with the approved deliverable's expected relationship and an observable failure condition: e.g. aligned calendar columns, a chart's marks contained in its plot, form controls fitting their cards, or a board's repeated cells having the required proportions. Equal area, square cells, and target size are requirements only where the task calls for them. A UI with no such invariant does not need this measurement method.

1. Run the stable output in a real browser. Identify relevant initial/empty, populated and after-interaction states and desktop/narrow viewports; include zoom or text/locale changes when the criterion depends on them. Record browser/version, viewport CSS-pixel width and height, page/visual-viewport scale or zoom, device pixel ratio, content/interaction state, and probe method/version. Note any unavailable states or engines.
2. Measure `getBoundingClientRect()` (or equivalent rendered boxes) for the container and the rows, columns, cells/items and interactive children that determine the invariant. Derive row/column membership from the actual structure or coordinates, rather than assuming a uniform DOM order. Record counts, per-row/column widths and heights, extrema/spreads, alignment/aspect/containment as relevant, and the container's *content* area when using it as a target (account for borders/padding). Choose an explicit tolerance in CSS px appropriate to rounding and the specific criterion; compare measured values to the expected relationship. Measure **all** repeated units when the invariant covers all of them; sampling is sufficient only if the stated criterion and risk permit it, and any unmeasured units remain unverified.
3. Repeat after population and meaningful interactions and at relevant responsive widths; state pass/fail for each applicable criterion and state. Document width/no-overflow, screenshots, contrast, focus, keyboard/pointer and accessible names are separate observations. Screenshots or expert visual judgment may reveal a problem but cannot establish a numeric CSS-pixel bound; DOM geometry cannot establish contrast, accessibility conformance, or actual user success. Report which input modes, assistive technologies and users were actually tested rather than inferring results.

**Bounded example — 10×10 populated board, not a default for other grids.** If this board's requirement is 100 equal-size square cells in ten equal rows/columns with dark-square buttons fitting their cells, check all 100 cell rectangles indexed by each row and column, plus relevant button rectangles. Compare each cell's width with its height, row-height and column-width spreads, the board content width/10 and height/10 targets, and button bounds against enclosing cells. For the historical Chrome 154, DPR 1, 100% zoom trial at 1440×900, 390×844 and 320×720 CSS px, ≤0.5 CSS px is a suitable *trial-specific* tolerance for these differences. The started game had row-height spreads of about 52.64, 25.94 and 20.67 CSS px respectively while columns varied by at most 0.016 CSS px; the page did not overflow horizontally. Thus a no-overflow check passes but the populated-row invariant fails at every width. An empty-board pass cannot stand in for a populated game.

For diagnosis only, after saving baseline measurements, an isolated in-memory `board.style.gridTemplateRows = 'repeat(10, minmax(0, 1fr))'` counterfactual can show whether track sizing explains the difference. Re-measure the same states and widths, label the override as a control, and keep the original result failed; this is neither a product edit nor a prescribed CSS fix. If no compatible real browser runs, mark the rendered criterion **unverified** and specify the prerequisite and next check; static CSS, HTTP, mocks and screenshots are not substitutes.
