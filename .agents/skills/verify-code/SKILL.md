# Verify code

**Inputs:** stable named code output/attempt, unit criteria and approved boundaries, repository rules, own attempt path.

**Procedure:**

Linked own-unit investigator evidence may be the applicable primary report set and assigned planner integration basis per protocol. Inspect relevant reports/material sources and their current identity/coverage/interactions; summary/count assertions are no substitute. Preserve selective renewal and affected gaps/owner/action without bypassing authority, full discussion or selected-level readiness. The set does not replace independently derived expectations or any required real execution below.

Before reading the producer implementation/solution, read the approved criteria/current review and establish the independent expected-behavior basis below. Source inspection and tests may refine failure hypotheses, never define the oracle by copying actual implementation output.

1. Inspect the actual diff and relevant surrounding behavior; distinguish changes made by the producer from existing work. Read relevant tests and project verification commands.
2. Run focused tests or checks that exercise the outcome and plausible regressions. Review untested behavior, edge cases, and adherence to inherited constraints; run broader checks only when justified by findings or repo rules.

   Establish falsifiable expectations first from exact approved criteria/current review and applicable version-scoped primary documentation, independently of producer conclusions or implementation-computed expected values. Use meaningful normal/error/recovery/counterexample and affected regression cases; independently calculate expected numbers where relevant. Retain actual distinct verifier invocation/report/receipt, linked own-unit investigator, stable target/revision/source/variant and the protocol's per-criterion environment/versions/prerequisites, cwd/exact command/input, expected versus observed output/exit/result artifacts, execution/support statuses and limits/owner/action. Do not confuse exit 0, build, test-plan approval or attempt completion with all criteria passing.

   **Published executable teaching, even Markdown:** in a clean isolated copy inside your own attempt, reconstruct only the student-facing published files/support, imports/exports/entry point, pinned runtime/framework/dependencies, commands and actual exercise-to-solution edits. Map instructions to resulting files and retain original/edited identities. Read approved exercise behavior and establish the independent expectation basis before inspecting the solution. Execute the published examples and actually edited solutions using published cwd/commands/input and relevant actual browser, not the producer's working screen or copied result fixture. Check intermediates as well as final values and fitting invalid-input/recovery/counterexamples. Missing instructions, imports/wiring, incompatible versions or wrong solution are findings: no private repair, extra scaffolding, silent upgrade or mock expected working screen. A checker-owned capture runner may faithfully execute the published recipe, never fill instructional gaps. Preserve failed target/results; only the producer publishes a repaired new stable variant for a new distinct verifier reconstruction/check.

   Where a claim depends on actual framework or browser behavior, execute the published version-matched application/dependencies and relevant real browser. Static inspection, builds, HTTP success, mocks and screenshots do not substitute for required execution. Missing compatible tools/prerequisites keep affected criteria pending/blocked and unverified with owner/action; do not install automatically or change support/acceptance. Keep executable correctness, technical prose correctness and actual learner effectiveness separate; a learning claim requires fitting approved actual participant/task/method/results, not code passing. Prose without executable content uses domain checks in `check-outcome`; no universal TDD or broad suite.
3. For a UI-bearing change whose approved outcome depends on rendered layout, spatial relationships or shapes, first derive the expected invariant from the deliverable requirements. Consult [rendered UI checks](references/rendered-ui-checks.md) on demand; measure in a real browser across relevant initial, populated, after-interaction and viewport states. Check geometry separately from overflow, contrast and focus. If the browser is unavailable, mark the browser-dependent criterion unverified and report the prerequisite; do not substitute screenshots or static inspection for a rendered measurement. Keep non-UI checks proportional.
4. Report the exact commands, outcomes, failures, and limits per criterion. Do not fix source or claim a test proves behavior it did not exercise.

5. Deliver own actual result artifacts, detailed report and separately assigned concise user summary (exact target/revision, actual investigator/checker, what ran/material statuses, proof links, limits/next action). Return only the protocol receipt with their paths; actual summary read/relay belongs to the orchestrator before outcome state update. Missing result/summary is a gap/blocker, never an invented successful run. Keep all reconstruction/evidence writes within your assigned own attempt; never edit delivered solutions or authoritative state.

**Output:** verifier-only report with checked revision/attempt and evidence; compact receipt per `.agents/workflow/protocol.md`.

**Stop/escalate:** output changed since handoff, necessary tests cannot run, approval mismatch or consequential conflict. Return a specific blocker for reconciliation.
