# V1 trials and acceptance

First perform the three walkthroughs below with proposed briefs and decisions. Then run small **live agent** sessions in disposable workspaces using available models, after [manual installation](install.md) and deliberate checkpoints. Do not fabricate a user approval during a live trial; a human explicitly grants it. Keep trial work out of reference projects and compare behavior to `.agents/workflow/protocol.md`. Record the model and harness version, the worker receipt, attempt/report paths, actual write paths, and each deviation; revise the smallest rule or skill that fails. Source-only fixtures live in `fixtures/`; use the [lookup](install.md#oldnew-source-path-lookup) for older literal fixture paths.

## New software endeavor

Ask for a tiny new tool with one checkable first outcome. Start at root U-0001: permit bounded investigation and draft its brief without an approval; stop before producing the tool. Present its outcome name/context and exact U-0001@revision-1 for actual approval. Explicitly select the tiny bounded group with the user and record its justified no-split readiness, or have a planner prepare child U-0002 if semantic evidence warrants it. Do not enter U-0002 until the user explicitly approves that ID/current revision in U-0001's checkpoint section; then invoke its distinct own-unit investigator as its first entry and consume the applicable report before substantive downstream planning or dependent production. Produce an authorized ready leaf, verify its stable named attempt, reconcile parent criteria separately. In a fresh session, identify group/wave readiness and current authority from briefs/checkpoints without the previous chat. Use the substantial uneven-depth scenario below to test breadth; this tiny case is not a one-child cap.

## Existing-code issue

Use a disposable small codebase with an observable defect, a relevant test, and a local `AGENTS.md` rule. Frame a bounded issue root; inspect and diagnose before choosing a fix. Check source references and competing causes in the investigator report. After approval, make a bounded change and have another worker verify it; a failed regression check must return to reconciliation, not mark the unit verified. Change a material acceptance criterion: the old checkpoint must not authorize advancing that new revision. Leave an unrelated root unaffected.

## Non-software endeavor

Frame a book chapter (or trip segment) with audience, boundaries and an observable review method. After adequate requirements/appropriate domain structure, expose a broad horizon and explicitly choose a bounded group with the user; prepare relevant siblings at each selected level, not the whole book/trip or an arbitrary first child. Introduce a changed inherited constraint—for example a new audience or trip date. Affected work returns to its parent decision and affected wave/path readiness; an unaffected authorized ready child can continue after preparation dispositions settle. Check the actual prose/plan against its criteria rather than pretending software tests apply. Demonstrate a narrowly approved exception that does not erase the general decision elsewhere.

## Pass conditions across the three

- No worker enters a child lacking a matching parent checkpoint; root framing before approval is limited to drafting.
- No worker treats tool permission approval as scope approval or silently overrides a consequential inherited choice. Material revision invalidates the old unit authorization without unnecessarily pausing unrelated units.
- Investigators and verifiers write only their own attempt artifacts. Each worker final message is a bounded receipt, with substantive detail in a real report path. If this repeatedly fails, investigate a validating adapter after documenting the failures.
- Verifier targets a stable named output, records checks that could fail and their limits; reconciliation uses this evidence before marking a unit or its parent verified.
- Fresh-session recovery works from briefs, checkpoints, applicable decisions and referenced evidence; model selection and skill discovery are observable. Parallel producers, if tried, own disjoint output paths.

An installed example is a real trial only when agent behavior, approvals, and outputs have been observed. The scenarios above are also usable as manual contract walkthroughs without consuming model tokens.

### Software: shared delivery with uneven depth

Use a project for offline field notes with reviewed requirements for draft recovery, finished-note history and export, plus conditional testing/visual-review basis for the actual selected interfaces. The broad horizon includes capture/recovery, history, export and future team sharing. Propose project-specific categories such as “reliable local work” and “distribution”; explain their relationships without treating them as mandatory unit levels. Explicitly ask the user to select **reliable local work and export** as the bounded delivery group, retaining sharing as a later horizon. Lead with those names/context, then exact prepared IDs/revisions in real checkpoint requests.

At the first selected level address capture/recovery, history and export siblings' outcomes, dependencies, readiness and finer boundaries before descending into capture. History may be a justified coherent leaf; capture may need independently reviewable editing and recovery outcomes. Export may use a separately acceptable packaging module with an agreed consumer contract: given a finished note and attachments, it produces a portable package with defined missing-attachment/error behavior and a failure-detecting round-trip check. Compare no-split, vertical flows and a reusable packaging capability using actual acceptance/retry evidence; do not require an artificial UI slice for the module or accept a file/layer label alone.

Checkpoint ready siblings in their appropriate parents, then invoke each entered child's distinct investigator and consume their findings before the next selected wave. Preserve the justified history leaf while preparing capture's finer horizon. If attachment format is unsettled, retain export's deferred/blocked requirement, reason, owner/action (user to resolve format through orchestrator), dependency impact and reconsideration basis (reviewed format decision). A dependent “share portable package” path stays blocked; independently ready history can deliver after all selected preparation dispositions are reconciled and its own gates hold. Preparatory requirements/format comparison outputs can establish readiness under their own authority before the barrier. Parallel ready capture/history production requires genuinely disjoint outputs and settled dependencies; a shared storage file needs sequencing or different settled ownership.

Resume from files after the first wave with an isolated history leaf marked active: expect lookup of the coordinating Work split/Relationships, actual selected group, current/completed wave, deferred export and next bounded action rather than immediate history production from state alone. Change an agreed retention requirement: renew affected same-unit evidence where material, revisit capture/history dependencies and matching material revision/D/checkpoints, preserve unaffected export history and pending disposition. For a cross-parent group keep one coordinating group record; each parent's named child checkpoints remain local, linked and single-writer. Child PASS is neither wave completeness nor parent proof; parent coverage/coherence/integration must be independently checked after outcomes settle.

### Book: useful breadth without uniform depth

Use a practical book for new community-garden coordinators. Reviewed requirements cover seasonal planning, volunteer coordination and site accessibility, including novice explanation, usable worksheets, climate uncertainty and the expected depth of comparisons. Appropriate structure is a proposed reader progression, not software architecture. Expose the broad horizon (getting started, running the season, improving the site) and explicitly choose **running the first season** with the user, preserving later material dimensions and dependencies. Names/context precede prepared IDs/revisions; those labels are organization, not leaf proof.

At the selected level address a seasonal planning chapter, volunteer handover guide and accessibility decision guide before deeper chapter preparation. The handover guide may be one justified leaf with scenario/continuity checks; seasonal planning may have independently useful calendar and weather-contingency outcomes. The accessibility guide may be blocked on applicable local site constraints: retain the requirement, source gap, owner/action (assigned investigator to obtain applicable constraints under its own authority), dependency impact (site-specific recommendations wait), and reconsideration basis (current sourced constraints and scoped review). No need to enter that deferred child merely to record the gap. Authorized discovery/preparation can establish those prerequisites; independently ready handover work may advance after group dispositions settle, without pretending deferred accessibility completes book criteria.

Prepare only the next useful sibling wave; obtain named current-revision approval in each child's appropriate parent checkpoint before invoking its distinct own-unit investigator as its first entry, then consume the applicable report before substantive downstream planning or dependent production. Keep uneven depth rather than inventing a child for every worksheet. Inspect prose against audience, terminology, scenario usefulness, cross-chapter continuity and actual domain sources; do not claim a reader study or executed gardening season. On file-only resume recover current wave and deferred impact. A changed audience or climate scope returns affected paths through evidence/review and material authority gates, not a global freeze or full-book expansion. Any later executable teaching included in a book still routes through `verify-code`.

## Clear communication across all five roles

Check [clear-communication](../../skills/clear-communication/SKILL.md) against two independent requirements: writing quality and understandable terms. Passing either cannot compensate for failure of the other. Freeze a named source target (the exact source snapshot to be checked) with full original bytes and an inventory of the 18 pre-existing skills, roles and protected methods; the added skill gives 19 source entries. Check runtime discovery, full configured role prompts and actual full loading of both common skills separately. Use a real distinct verifier and an isolated verifier-owned workspace, preserving original failures and named targets.

Use small actual invocations of every full role. Carry available reader context and links in assignment inputs; combine cases rather than build a broad benchmark:

| Role | Substantive case and required observation |
| --- | --- |
| Orchestrator (coordinator) | Actually delegate a unit question to a fitting worker, receive its report/compact receipt, read the separately owned answer artifact and relay the answer. Explain an essential term the user has not seen, even if an internal report defined it. |
| Investigator | State a bounded finding and its evidence early; explain an unfamiliar term, keep uncertainty and preserve exact IDs/commands. Write only owned attempt artifacts and return the fixed receipt. |
| Planner | Compare approaches and explain a recommendation's practical reason or consequence without inventing user agreement. Preserve current authority and sole-writer boundaries. |
| Producer | Write a standalone explanation, then continue the same problem without repeating definitions. Start a new problem with relevant meanings again; a fuller-detail request must retain all requested substance. |
| Verifier | Reject seeded failures by citing exact passages and the failed dimension. Check a correct expert-context passage without needless basic definitions. Write its own report and separate short outcome summary; do not repair the target. |

For each substantive passage, record writing, terminology and fidelity findings separately. Writing checks cover answer placement, logical order, coherent paragraphs, concrete actors/referents and useful reasons without filler. Term checks cover practical first-use meanings in familiar words, consistent names and actual reader-visible context; acronym expansion or a link alone can fail.

Include these negative controls: deliberately flawed examples that the check must reject. (1) “The report was clear. This changed it, so that is ready”: familiar words but unclear referents and reasoning. (2) An answer that correctly defines “idempotent” as repeating a request without repeating its effect, then buries the recommendation beneath repeated background: terms pass, composition fails. (3) For a new reader asking which request value a payment retry should keep, “Reuse the original idempotency key on the retry” answers clearly but leaves the essential term unexplained. Seed lost-uncertainty, altered-identifier and false-approval traps as well. For example, preserve supplied `U-9037@revision-1`, `pending-unrun` and `opencode debug skill` exactly; a successful source check must not become a claim of observed role loading or user approval.

Record actual runtime/model/config/prompt/source identities, invocation/session IDs, inputs, full-load traces, prose, receipts, writes and result paths. Review complete source changes against original bytes for retained authority, evidence, ownership, lifecycle/domain methods and actual answer/summary read-relay duties. Append observations to `trial-results.md` only after execution, name the changed final target and obtain a new distinct scoped check; earlier role observations apply only to unchanged instruction bytes. Missing prerequisites leave required checks blocked or unrun, not PASS. These checks establish bounded rule-following and prose observations, not a reader study measuring people's comprehension or a guarantee enforced by tools.
